# Document 24 — State Management & Event Bus Architecture

Version 1.0

---

# Purpose

This document defines how state flows throughout SYNAPSE.

Rather than allowing every system to directly communicate with one another, SYNAPSE uses a predictable, event-driven architecture.

The objective is to ensure every subsystem remains independent, testable, scalable, and maintainable while enabling rich interactions between AI, rendering, animation, world simulation, and user input.

State should always have one owner.

Communication should always have one path.

---

# Core Philosophy

State is ownership.

Events are communication.

Rendering is consequence.

No system should directly mutate another system's state.

Every interaction should propagate through well-defined events.

# Synchronization Rules

Stores never synchronize directly.

Synchronization occurs through events only.

Example

```text
Hover Project

↓

Interaction Event

↓

Experience Store

↓

Camera Event

↓

Camera Store

↓

Lighting Event

↓

Lighting Store

↓

Renderer
```

Each system remains isolated.

---

# Performance Rules

State updates must remain minimal.

Avoid:

Deep object mutation.

Large nested structures.

Frequent rerenders.

Unnecessary subscriptions.

Use selectors aggressively.

---

# Error Handling

Invalid events are rejected.

Store corruption should trigger recovery.

Event failures should never crash the renderer.

Systems should fail independently.

# Common Failure Modes

Avoid

Global mutable state.

Event loops.

Circular updates.

Business logic inside components.

Direct store mutations.

Multiple owners.

Duplicated state.

Excessive subscriptions.

Anonymous events.

# Definition of Done

The state architecture is complete when:

Every piece of data has one obvious owner.

Every system communicates through events.

Debugging complex interactions is straightforward.

State updates remain predictable.

Adding a new subsystem requires minimal architectural changes.

The codebase scales without increasing coupling.
